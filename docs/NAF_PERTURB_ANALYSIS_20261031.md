## 内存事故与恢复

事故来自根代理新增私有GT统计。`filled`读取后未转bool，bool核心与uint8按位与仍为uint8，
`gt[mask]`遂把它当整数行号。1936×2584掩码展开到1936×2584×2584，
uint16结果约24.078GiB，转uint32再申请48.156GiB，合计超过62GiB容器限额。
现场SSH和网页终端失去响应，没有取得现场PID、RSS峰值或内核OOM日志，不编造这些证据，
也没有把本地SSH断连误报为已终止远端。

用户重启后，仅用标准库读NPY头：instance_map为uint16，original_covered/filled/residual_unknown均uint8；
本地3×4数组已复现索引扩维。已归档原执行脚本，修正为显式bool、同shape二维检查、
准确读取original_covered并排除residual_unknown。仅完成编译与微型检查，未恢复大图统计。
训练数据读取、独立256配对原本正确转换掩码，不受该诊断错误影响；前三例读出在GT统计之前已完成。

恢复核验不导入torch/numpy、不加载模型：新旧权重及相关9文件SHA全匹配，无残留大型分析进程。
核验后容器实际占用约1.22GiB，其中匿名内存.276GiB、文件缓存.919GiB。
宿主机`/proc/meminfo`约503GiB不是容器预算，应读取cgroup的62GiB上限。
随后仅收集已有9个小图/JSON共1.49MB，收集进程设256MiB虚拟地址上限，峰值RSS约12MiB。
本轮不再恢复推理；后续此类CPU统计应与GPU推理解耦、限制内存并记录PID。
