## 分层定位

| 分析方法 | 证据 | 结论 |
| --- | --- | --- |
| 状态／源码／文件摘要核对 | 权重全部FP32，状态、源码、100张原文件和种子与原记录相同 | 没有发现导出降精度、错模型、错原图或短测重新编号种子的错误 |
| 五图独立进程各重跑三次 | 最终实例、类别、连续地图及实际噪声逐值一致 | 当前机器稳定，不能把差异归为同机每次随机漂移 |
| CuDNN TF32关闭，或注意力改数学实现 | test101仍147→146，test116仍402→391，边界与原记录差异基本不变 | 这些计算设置不是大部分差异的来源 |
| 原服务器raw语义概率与本地概率比较 | test101 MAE 1.4743e-5；在原实例图上换本地概率，类别变化0；在本地实例图上换原概率，类别变化也0 | 本例观察到的类别变化主要由实例区域范围改变引起，不能称语义权重错载 |
| 固定CUDA噪声布局，保持模型与其他计算设置 | 本机布局原型在三种种子、两个编译目标下都逐值复现原生torch.randn；换为4090布局后，五图差异显著缩小且再次重复逐值一致 | D5a跨GPU的实际噪声输入不同是本次主要原因 |
| 固定噪声后再关闭TF32 | test101预测F均面积变化约+1.056%，原设置约−0.003%；数学注意力也未消除残余差异 | 保留原精度设置，不因“更严格”就更改已评分计算契约 |

这里的TF32是允许卷积使用较短有效尾数的一种加速模式；AMP始终关闭，权重始终FP32。
没有通过半精度／量化改变模型，也未宣称全部CUDA算子均采用同一实现。

## CUDA噪声为何受显卡影响

D5a的首步不是完全无随机量。每次`restore_first`新建CUDA generator并设置种子，
在最终退化步将条件图加上`0.03 × 标准正态噪声`。固定种子固定随机序列，
但PyTorch2.8的CUDA实现还依赖显卡核心数决定随机序列如何写入大张量。

对于连续FP32 `[1,3,1024,1024]`，CUDA block为256线程，normal4一次产生四值。
`G=min(ceil(N/256), SM*floor(maxThreadsPerSM/256))`，写入跨度`S=256G`。
参考4090为128SM、每SM1536线程，G768；实测5060 Laptop为26SM、1536线程，G156。
同种子由此写入不同像素噪声；这改变了恢复器实际输入，而不只是浮点舍入。
依据：[PyTorch2.8 CUDA distribution源码](https://raw.githubusercontent.com/pytorch/pytorch/v2.8.0/aten/src/ATen/native/cuda/DistributionTemplates.h)、
[CUDA generator源码](https://raw.githubusercontent.com/pytorch/pytorch/v2.8.0/aten/src/ATen/cuda/CUDAGeneratorImpl.cpp)、
[NVIDIA cuRAND设备API](https://docs.nvidia.com/cuda/archive/12.8.1/curand/device-api-overview.html)。

私有原型用显式grid模拟该原始布局，先G156校验原生随机数，再G768诊断参考输入。
保留Philox4x32-10、normal4、种子和offset0；没有直接换成CPU随机数或零噪声。
这只覆盖本项目每次新建generator的首步路径，不适用于任意已消耗的随机流。
