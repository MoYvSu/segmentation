# TensorRT 推理中的 batch：当前设置与后续优化

截至2026-11-01，当前整合流程已经使用五个TensorRT引擎，但1024局部窗口仍逐个处理。NAF的小块推理已经采用批量处理。已完成的引擎构建、实际batch检查及小样本结果见[全模块加速记录](FULL_ACCELERATION_20261101.md)；本指南不把这些结果解释成1024批量推理的收益。

## 1. 一次前向到底处理几个块

一次“前向”就是调用一次网络得到输出。Batch是这次调用同时接收的独立样本数，记作B；B4表示一次接收4个块，仍返回4份对应结果。

| 角色 | 当前引擎输入 | 当前批量设置 |
|---|---|---|
| D5a首步恢复 | RGB图像与恢复状态，均为`[1,3,1024,1024]`；另有时间索引 | 静态B1 |
| SAM2 Hiera trunk | RGB图像`[1,3,1024,1024]` | 静态B1 |
| 语义头 | 四级特征，各自B1；需要时另接收图像 | 静态B1 |
| affinity头 | 四级特征，各自B1 | 静态B1 |
| NAF边界恢复 | 单通道边界小块`[B,1,256,256]` | 动态B1–16，通常16，尾批可小于16 |

语义头和affinity头接收的是1024图像产生的多尺度特征，并非再次直接接收1024 RGB。当前正式调用中，NAF观察到16的满批及10、15的尾批；模块检查还运行过B1。这些是256小块的batch，不是一次处理16张1024图像。

当前局部分支为：

```text
一个1024窗口 → D5a恢复 → trunk提取特征 → affinity头 → 该窗口边界图
```

局部窗口不额外调用语义头。恢复图全图语义与原图全图语义仍是独立的全图计算，分别参与划分与最终实例投票。当前窗口循环见[affinity_native_views.py](../tools/affinity_native_views.py)，NAF的分批循环见[boundary_rgb_monitor.py](../tools/boundary_rgb_monitor.py)。

## 2. min、opt、max不会自动替我们分批

当前NAF的TensorRT配置为`min=1、opt=16、max=16`：

- `min`：允许的最小批量。
- `opt`：构建时着重优化的批量。
- `max`：允许的最大批量。

这只是引擎接受输入的范围。调用程序仍负责准备输入、选择本次批量、设置实际形状和分配输出。`opt=16`不要求必须攒够16份才运行，也不保证16在所有场景下最快；送入超过范围的批量也不会自动拆分。[NVIDIA动态形状说明](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/inference-library/work-dynamic-shapes.html)

例如，一张图产生42个NAF小块，当前程序会分成：

```text
第1次：16个256小块
第2次：16个256小块
第3次：10个256小块
合计：42个小块，3次NAF前向
```

第三批直接使用B10，不必补成16。批量范围、实际分组以及“每个块放回哪里”是三件需要分别实现的事。

## 3. 12个1024窗口改成B4会怎样

以下仅是未来调度示意，**当前1024局部B2/B4尚未实现，也没有GPU实测**。

| 批次 | 同时送入的原窗口 | 局部分支 |
|---|---|---|
| 第1批 | 1、2、3、4 | D5a(B4) → trunk(B4) → affinity(B4) |
| 第2批 | 5、6、7、8 | D5a(B4) → trunk(B4) → affinity(B4) |
| 第3批 | 9、10、11、12 | D5a(B4) → trunk(B4) → affinity(B4) |

当前逐窗处理需要12次D5a、12次trunk和12次affinity调用。示意中的B4调度分别需要3次，每次计算4个窗口；需要完成的图像计算量没有因此变成四分之一。这里也未计入独立全图语义、NAF和CPU后处理。

实现时要完成两个动作：

1. **组合输入（stack）**：把独立窗口放在批次维，得到`[4,3,1024,1024]`。如果每个窗口已经带有B1维度，应沿batch维拼接，而不是再增加一维。
2. **分回结果（scatter）**：按原窗口编号取出4份输出，分别使用各自的坐标、有效区域和padding记录裁回原尺寸，再按原窗口顺序调用`BlendMap.add`。

原25%重叠、拼接权重、窗口顺序以及拼完后的全图划分都应保持。尤其不能按GPU任务完成顺序随意累加重叠区域：浮点累加顺序变化本身也可能产生数值差异。

当前[infer_accelerated.py](../tools/infer_accelerated.py)没有可用的`--batch-size`开关。真正的1024 B2/B4需要另行导出支持该批量的图、构建匹配引擎，并修改窗口分组、时间索引、输出拆分及调用审计。仅修改运行参数或引擎profile不能完成这些工作。当前NAF允许B1–16也不意味着公开入口已经提供任意切换批量的操作。

这项调整无需重新训练模型：权重保持，只重建支持目标batch的引擎并修改输入调度；其数值和效果仍需单独验证。

## 4. 不同窗口会不会互相影响判断

在本模型保持推理模式、权重冻结且没有跨样本运算的条件下，把窗口打包处理，在数学上仍是各自独立推理，不会让一个窗口参考另一个窗口的内容。

当前SAM2、D5a和NAF主要使用LayerNorm，FPN使用GroupNorm。它们的归一化范围不包含batch维。FPN配置里的旧名称`use_bn`实际选择的是GroupNorm，见[fpn_decoder.py](../models/fpn_decoder.py)。因此不能仅看到名称中有“batch”就推断当前网络需要共同统计多个窗口。[LayerNorm说明](https://docs.pytorch.org/docs/2.8/generated/torch.nn.LayerNorm.html)、[GroupNorm说明](https://docs.pytorch.org/docs/2.8/generated/torch.nn.GroupNorm.html)

一般的BatchNorm在默认`eval`模式下读取训练时保存的统计量，也不依赖当前批次；但`track_running_stats=False`时，即使eval仍使用当前批次统计。这是需要核对的例外，并非当前GroupNorm/LayerNorm的行为。[BatchNorm说明](https://docs.pytorch.org/docs/2.8/generated/torch.nn.BatchNorm2d.html)

数学等价仍不能保证结果逐位相同。不同batch可能使用不同GPU算法或浮点累加方式，得到微小数值差；阈值、种子和分水岭可能放大其中一部分差异。PyTorch也明确说明，批量计算与逐样本计算不保证逐位一致。因此批量候选仍需比较最终实例、类别和官方得分，不能预先称为无损，也不能把差异直接定性为精度下降。[PyTorch数值精度说明](https://docs.pytorch.org/docs/2.8/notes/numerical_accuracy.html)

## 5. B4/B8为何可能更快，也可能不划算

批量处理可能减少调用和同步开销，让GPU更充分地利用计算资源。需要分别看两个指标：

B1也已经在GPU内部并行计算一块图的许多像素、通道和特征，并不是只有一个计算单元在工作。增加batch是在此基础上加入更多独立窗口；如果B1已经充分占用GPU，收益就可能有限。

- **吞吐**：连续处理很多图或窗口时，每秒完成多少份结果；这是当前优化目标。
- **单张延迟**：从一张图开始处理到结果完成花多久。为凑批而等待可能增加延迟。

B4/B8不会自然带来4倍/8倍提速。GPU可能在B1时已经较忙，增大batch还会增加中间特征、注意力和输出所需显存。四个窗口共享同一套权重，无需复制四个模型；增加的显存主要来自同时保留四份计算中间结果。显存占用的主体不只是最初的RGB输入。16个256小块的总像素数才等于一个1024块，因此不能从“NAF可以B16”推断“1024网络也可以B16”。

4080 SUPER属于Ada架构。NVIDIA特别指出，这类GPU有时反而在较小batch下因缓存利用更好而具有更高吞吐，需要尝试不同批量。[NVIDIA批量性能说明](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/optimization.html)

GPU批量也不会自动加速CPU上的种子生成、分水岭、逐实例投票和末端整理。即使网络部分明显变快，整图收益仍受这些步骤、读写及拼接开销限制。

## 6. Batch和多stream的区别

Batch类似“一次送入4个窗口”；多stream类似“几条GPU任务队列尝试同时推进”。它们可以结合，但不是同一个开关。

多stream需要安排各自的执行上下文、输入输出buffer和同步关系；不同队列仍会争用同一张卡的计算、缓存和显存资源，增加队列数不等于增加显卡数量。当前运行桥也不能靠把同一个context同时交给多个任务就安全获得并发。[NVIDIA多stream说明](https://docs.nvidia.com/deeplearning/tensorrt/11.4.1/performance/optimization.html)

## 7. 后续怎样验证

建议把1024批量调度作为独立候选，先比较B1/B2/B4，继续使用同一权重、FP32、TF32关闭、原零噪声和后处理规则。B8是否值得扩大，应由前面测得的显存和吞吐决定。

每组采用相同窗口集合与拼接顺序，分别记录预热后整图耗时、窗口吞吐、峰值显存及最终输出差异，并处理不能整除的尾批。构建成本单独记录，不作为当前大批量使用场景的否决门槛。通过小样本检查后，再以完整部署输出和官方得分决定是否采用。

本轮已完成的全引擎整合仍是“四个1024路径角色B1＋NAF满批16/尾批”的实现；本指南没有新增引擎、改变调度或启动批量实验。
